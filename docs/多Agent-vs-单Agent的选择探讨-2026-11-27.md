# 多Agent vs 单Agent 的选择探讨

- 日期：2026-11-27
- 来源：`daily/2026-11-26.md`、`daily/2026-11-27.md` 实践笔记，以及 2026-11-27 晚间通话中的校正
- 性质：探讨记录，不是开工清单；现有总调度 / 多角色设计稿保持不动

## 一句话结论

多 agent 并行、总调度分派、看板跟踪，可以作为后续形态记下来；但各 agent 的执行程度和产出稳定性差异很大，所以当前先从单个 agent 的具体场景做熟，而不是一开始就拆很多条、分给很多角色。

## 手头这些 agent 目前怎么用

依据 11-26 实践笔记中的用法，而不是重新划分职责：

- 编码主要用 Cursor Composer 2.5。在已知确定性框架下，项目框架、完整闭环、增量需求和修 bug 的效率比较高。不要开 fast 模式，消耗大约是普通模式的 2 到 3 倍。
- 决策和规划有时会用 ChatGPT 网页版，深度较高；决策、规划再到实施，主要用 Grok Bot 和 OpenMausBot，用来减轻中间反复思考的琐碎，把流程做完整。
- 简单问答用 Gemini，速度快，质量也不错。国内的 DeepSeek、Qwen 基本不怎么用。
- 测试和体验用过豆包工作、WorkBuddy、Qoder。感觉上豆包综合能力强一些，问题深度也还可以；Qoder 编码能力强一些；WorkBuddy 还没有深度使用，感觉一般，后续要在具体场景里再测，而不是先铺开角色。
- 笔记里提到小号额度充足、可以多角色测试。这只是条件，不是现在就要同时开很多条线。

11-26 还记过一个问题：这些桌面端能不能用消息通知或 webhook 来调度；如果不行，似乎只能靠定时检查。目标是在需要时并行产出多套结果做对比，或在主要 agent 忙碌时，让次要 agent 做补充。

## 曾考虑的多 agent 方案

同一天的笔记里，还设想过一套更完整的用法：

- 要有一个执行大脑或总调度，判断哪些内容要发散给多个 agent 分别出方案，哪些内容在空闲或忙碌时交给谁。凭感觉分配容易出错。
- 用看板列出各 agent 的运行状态和产出，这样任务多、步骤碎时，还能看见谁做了什么、结果在哪，不至于接不上之前的上下文。
- 讨论过由 ChatGPT 设计任务看板，task-os 桌面端做消息中转和展示。相关讨论见 [ChatGPT 对话](https://chatgpt.com/c/6b078c8a-ed44-83ea-9d52-e9d26a489c75)。
- 11-27 实践里还出现过「AI 角色分配师」和「敦促进度和反思角色」，以及一起找参考案例。这些仍是设想，按下面的校正，先不新建这些角色。

这套方案看起来比较完整，也能给一个整体观感，方便以后做调度和决策。它不是被否定，只是现在不作为主建设目标。

## 校正：为什么先选单 agent 场景

11-27 晚间通话里的校正是：思路可以先记着，但执行起来会碰到一个硬差别——各 agent 的执行程度不一样，预期和产出结果的稳定性差异很大。

因此选择是：

1. 从单个 agent 的具体场景入手，而不是一开始就分很多内容、铺很多角色。内容发布是当前最合适的切入例子。
2. 专门做这一条：对比结果，加入脚本和提示词，并参考网上已有案例，而不是先搭总调度再往里填任务。
3. 等一个场景做得比较熟练，再考虑加入更多；其他方面可以先做简单的。
4. 参考案例的价值在于少踩坑，并提高产出的性价比。自己从零铺一套多角色机制，开销大，还不容易看出哪一步真正有效。

## 眼下的取舍

- 多 agent 并行对比，加上总调度和看板，留作熟练之后的形态，不在本文里变成待办去开工。
- 当前优先把一条单 agent 场景做熟，首选内容发布：做、对比、补脚本和提示词，并对照公开案例。
- 现有文档 `roleandaction.md`（总调度与状态驾驶舱）和其他多角色设计稿不在这次改动范围内，本文只补充「先单后多」的选择理由。
