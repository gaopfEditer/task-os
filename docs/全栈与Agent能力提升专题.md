# 专题二：网站 + 全栈 + Agent 能力提升

> 面向：主要做网站与全栈、并要上 Agent 的人。  
> 原则：不再堆框架入门；把传统全栈往**生产级 Agent 系统**延伸，并补 Agent 特有能力。  
> 配套：见《软件开发能力边界专题》（平台边界与工程现实）。

---

## 0. 2026 年现实与定位

简单调 API 的「AI 包装器」已经不值钱。更需要的是：把 Agent 做成**可靠、可控、可观测、成本可控**的系统。

全栈背景是优势：你天然懂状态、权限、API、数据流和前端体验——这些正是生产级 Agent 的底座。目标不是「更会聊天」，而是把 Agent 当成**有状态、有权限、会失败的分布式系统**来设计。

| 别再过度投入 | 该持续投入 |
|--------------|------------|
| 追最新多 Agent 框架名 | 单 Agent + 清晰工具 + 评估做稳 |
| 只会调 Chat Completions | 工具 schema、权限、trace、成本路由 |
| 把 Agent 当聪明对话框 | 流式体验 + 失败可恢复 + Human-in-the-loop |

## 1. 必须扎实的全栈基础（Agent 的底座）

这些不是过时技能，而是被 AI **放大了重要性**。

### 1.1 TypeScript 端到端

| 点 | 为什么 | 细化到能动手 |
|----|--------|--------------|
| 前后端统一类型 | Agent 输出常非结构化，类型是第一道防线 | 共享 `packages/types` 或同仓导出；API 入参/出参与工具结果同一套类型 |
| 工具调用 Schema | 模型乱填参数是常态 | 每个工具用 **Zod / JSON Schema** 定义；运行时 `safeParse`，失败返回**结构化错误**给模型重试，而不是抛未捕获异常 |
| 结构化输出 | 下游要落库、渲染、触发下一动作 | Prefer `response_format` / tool_calls；禁止「从自然语言里正则抠字段」作为主路径 |
| 窄类型优于 any | 工具一多，any 会让权限漏洞藏不住 | 工具名用联合类型；按工具名做 exhaustive switch |

**练习**：写 3 个工具（查库、写库、发通知），强制 Zod；故意让模型传错参，确认错误能回到对话循环而不是 500。

### 1.2 现代前端（以 Next.js App Router 为主）

| 点 | 为什么 | 细化 |
|----|--------|------|
| Streaming UI | 用户感知的是「边出边看」，不是等整段 | Token/事件级流式：文本增量、工具开始/结束、部分结果卡片；用 Vercel AI SDK（或同类）的 `useChat` / `streamText` 模式 |
| 工具结果渐进渲染 | 工具可能跑几秒到几分钟 | 先占位 → 进度/中间态 → 最终卡片；失败态可重试 |
| Human-in-the-loop | 危险操作不能自动执行 | UI 上明确「待确认」卡片：批准 / 拒绝 / 改参；未批准前工具不真正副作用 |
| 乐观更新与回滚 | Agent 写操作失败率高于普通表单 | 本地先显成功态，服务端确认失败则回滚并说明原因 |
| 长会话内存 | SPA/对话页开很久会泄漏 | 虚拟列表聊天气泡；大工具结果分页或外链；卸载时取消 in-flight fetch |

**验收体验清单（前端）**

- [ ] 首 token / 首事件有感知（骨架或光标）
- [ ] 工具调用有独立进度条或步骤条，不只塞进 assistant 文本
- [ ] 用户可中止生成；中止后状态一致
- [ ] 危险工具必须点确认才执行
- [ ] 断网/超时有可恢复文案，不是空白转圈

### 1.3 后端与数据层

| 点 | 为什么 | 细化 |
|----|--------|------|
| PostgreSQL + pgvector | 关系数据 + 向量检索合一，生产常见 | 业务表与 embedding 同库或可事务关联；`user_id` / `tenant_id` 行级隔离；向量索引监控召回与延迟 |
| 会话与用户状态 | Agent 对话是长生命周期状态机 | 分清：`thread`（会话）、`run`（一次执行）、`step`（一步）；落库字段含 status、model、token、error |
| 权限模型 | Agent 不能无限权限 | 身份 = 真实用户（或服务账号）；工具级 scope；数据查询强制带租户条件，禁止「模型拼 SQL 直接跑」无审计 |
| 缓存与队列 | 控成本、扛慢工具 | Embedding/检索结果缓存；长工具进队列（BullMQ / 云队列）；前端订阅 run 状态而非同步死等 |

**数据模型最小集（建议）**

```
users / orgs
threads (user_id, title, created_at)
messages (thread_id, role, content, meta)
runs (thread_id, status, model, token_in/out, cost, started_at, ended_at)
tool_calls (run_id, name, args, result, status, latency_ms)
documents + chunks + embeddings (tenant_id, source, version)
audit_logs (actor, action, resource, at)
```

### 1.4 认证与安全边界

| 点 | 细化 |
|----|------|
| OAuth / OIDC | 用户登录与第三方连接（邮箱、工单、云盘）分开授权；Agent 用用户委托的 token，设过期与刷新 |
| 细粒度授权 | RBAC 不够时用资源级：哪张表、哪个项目、只读/读写 |
| 最小权限工具 | 每个工具声明 `scopes[]`；编排层校验，模型「想调」不够 |
| 密钥 | 模型 Key、第三方 API Key 只在服务端；前端只有 session |

## 2. Agent 核心工程能力（增量最大、最该补）

### 2.1 工具设计与调用

Agent 的行动能力几乎全靠工具。

| 实践重点 | 做到什么程度算过关 |
|----------|-------------------|
| 清晰 Schema | 名称、描述、参数、必填/枚举写清；描述写「何时用/何时不用」 |
| 超时 / 重试 / 幂等 | 每个工具有 timeout；可重试的标 `idempotent`；写操作带 `idempotency_key` |
| 结构化错误 | `{ code, message, retryable, hint }`，供模型或编排决定下一步 |
| 权限范围 | 工具内再验一次身份与资源，不信任「编排层说过了」 |
| 副作用分级 | `read` / `write` / `irreversible`；后两档默认要 HITL |

**反例**：一个叫 `doAnything(sql: string)` 的工具。  
**正例**：`searchOrders({ userId, status?, limit })`，内部强制 `userId = session.userId`。

### 2.2 编排模式

| 阶段 | 建议 | 何时升级 |
|------|------|----------|
| 起步 | 单 Agent + ReAct（思考→工具→观察→再思考） | — |
| 有分支/循环 | 显式状态图（如 LangGraph 类）：节点 = 步骤，边 = 条件 | 出现「必须审批后再继续」「失败回某节点」 |
| 多 Agent | 按角色拆（检索 / 执行 / 审核） | **仅当**单 Agent 上下文爆炸或职责冲突明显时 |

原则：**先简单跑通，再按痛点加复杂度**；不要一上来多 Agent。

### 2.3 内存与状态（四种别混）

| 种类 | 存什么 | 典型实现 | 常见坑 |
|------|--------|----------|--------|
| 执行状态 | 当前 run 走到哪一步 | DB `runs/steps` 或状态图 checkpoint | 只放内存，进程一挂就丢 |
| 会话上下文 | 近期消息窗口 | 滑动窗口 + 摘要 | 无限追加导致贵且糊 |
| 长期记忆 | 用户偏好、跨会话事实 | 结构化 profile 表 ± 向量回忆 | 和 RAG 文档糊成一锅 |
| 知识检索 (RAG) | 业务知识库 | 分块 + 向量/混合检索 | 把「聊天记录」当唯一知识源 |

### 2.4 RAG 工程（多数实用 Agent 都依赖）

| 环节 | 细化 |
|------|------|
| 分块 | 按标题/语义分块；保留 source、version、updated_at；代码/表格单独策略 |
| 检索 | 向量 + 关键词混合；必要时 rerank；按租户过滤 |
| 失效 | 源文档更新 → 重嵌入；删除 → 级联清 chunk |
| 注入 | 检索结果带引用；回答强制可追溯；低相关则如实说不知道 |
| 评估 | 离线：命中率、MRR、答案忠实度；上线：无引用率、用户点踩 |

### 2.5 MCP（Model Context Protocol）

| 能力 | 为什么要会 |
|------|------------|
| 写 MCP Server | 把现有内部 API/DB 工具标准化暴露给 Agent，避免每个产品重写适配 |
| 消费 MCP | 对接生态里的数据源与工具，缩短集成时间 |
| 与自有工具并存 | MCP 是边界协议；权限、审计、HITL 仍在你的编排层 |

**练习**：把你已有的 2～3 个后端 API 包成一个 MCP Server，再用同一套权限模型调用。

## 3. 生产化能力（决定能不能上线）

原型容易，生产难。2026 拉开差距的关键三件套：**评估 + 可观测 + 成本**，再加护栏与可恢复。

### 3.1 评估（Evals）

| 层 | 做什么 |
|----|--------|
| 离线 | 固定测试集：任务完成率、工具选对率、参数正确率、幻觉/忠实度、延迟与 token |
| 在线 | 采样真实会话；用户反馈；自动规则（是否越权、是否死循环） |
| 回归 | 改 prompt/模型/工具后跑同一套 eval，不过线不发版 |

没有评估 = 没有迭代依据，只能靠体感。

### 3.2 可观测性（Observability）

不只打日志，要有完整 **trace**：

- 哪一次 `run`、哪一步、哪个模型  
- 调了什么工具、参数与结果摘要、耗时  
- token 与估算成本、触发了哪条策略（路由、限流、护栏）  

工具生态：LangSmith、Langfuse、OpenTelemetry 等——选一个贯穿开发到生产，统一 `run_id`。

### 3.3 成本与延迟控制

| 手段 | 细化 |
|------|------|
| 模型路由 | 分类/简单抽取用小模型；复杂推理再用大模型 |
| Token 预算 | 每 run / 每用户日限额；超限降级或排队 |
| 缓存 | Embedding、高频检索、相同工具读请求 |
| 循环上限 | max steps / max tool calls；超时强制结束并返回已得结果 |
| 流式优先 | 降低「体感延迟」，即使总耗时不变 |

### 3.4 安全与护栏（Guardrails）

- 工具权限最小化 + 服务端强制校验  
- 危险操作 Human-in-the-loop  
- 防无限循环（步数、重复工具调用检测）  
- 防 prompt 注入（工具结果与用户输入隔离标签；检索内容不当指令执行）  
- 防越权（水平越权测例进 eval）  
- 参考 OWASP 针对 Agentic 应用的威胁模型做检查表  

### 3.5 失败处理与可恢复性

| 场景 | 期望行为 |
|------|----------|
| 工具超时 | 可重试则有限次；否则标记失败并让模型换策略或向用户说明 |
| 工具 4xx/5xx | 结构化错误进入轨迹；不可重试的直接终止该支路 |
| 长任务中断 | checkpoint；用户可「继续」同一 run |
| 明确终止 | success / failed / cancelled / needs_input，禁止无状态挂起 |

## 4. 提升优先级（务实顺序）

| 优先级 | 做什么 | 完成标准（可勾选） |
|--------|--------|-------------------|
| **P0** | 做一个完整全栈 Agent 并跑通 | 流式对话 + ≥3 个真实工具 + 登录权限 + 基本错误处理 + 一次 run 可在 UI/DB 追溯 |
| **P1** | 补 Agent 工程核心 | 工具 Zod schema；状态四分清；RAG 可引用；编排仍以单 Agent 为主 |
| **P2** | 生产化三件套 | 离线 eval 集；trace（模型/工具/token）；模型路由 + 限额 + 步数上限 |
| **P3** | 安全与治理 | 最小权限、HITL、审计日志、注入与越权测试用例 |
| **P4** | 按需加深 | 多 Agent；本地/边缘模型；更复杂记忆——**仅当 P0–P3 的痛点逼出来时** |

### 推荐练手产品（选一个做透，不贪多）

1. **带 RAG 的内部知识助手**（文档权限按人/组）  
2. **能调你自己后端 API 的业务 Agent**（查单、改状态，写操作 HITL）  
3. **客服/内部助手**（工单工具 + 知识库 + 转人工）  

重点不是功能多，而是：**流式体验、权限、错误处理、基本 trace** 四样齐。

---

## 7. 收束

- 先把**单 Agent + 清晰工具 + 好评估**做稳，再谈多 Agent。  
- 前端体验与后端可靠性同等重要：用户感知的是流式、工具进度、失败可恢复。  
- 把 Agent 当分布式系统：状态、权限、失败域、成本，全部显式设计。  
- 全栈优势要用在「端到端数据流与权限」，不要只用在「再包一层聊天 UI」。
