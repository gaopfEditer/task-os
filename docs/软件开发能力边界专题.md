# 软件开发专题：能力边界与仍值得深入的点

> 用途：开开发任务时对齐「平台能做什么」不够——还要知道「缝隙填满之后，真正难的是什么、和 AI 怎么接」。

传统桌面 / Web / 移动 / 后端的能力边界已经高度清晰。OS、浏览器沙箱、Android/iOS 运行时把「能不能做」框死了；框架和工具链把「怎么做」也填得差不多了。内存/资源、输入输出、第三方库、会话与权限隔离、展示与计算分离——这些都是正确的核心边界。

**剩余重点不在「能不能做」，而在更稳、更高效、更安全、更可维护，以及怎么和快速变化的 AI 层结合。**

---

## 0. 一句话总览

| 形态 | 硬边界 | 缝隙已填满的部分 | 仍值得深入 |
|------|--------|------------------|------------|
| 桌面 | OS 内核、驱动、硬件、权限 | UI、本地存储、常规算法、常见外设 SDK 用法 | 资源生命周期、崩溃分析、跨平台取舍、硬件深度集成、Profiling/GPU |
| 网站 | 浏览器沙箱 | DOM/图表/常规 SPA、常见权限弹窗 API | WebGPU 等精细能力、工程化与长会话内存、边缘协作、前端安全模型 |
| 后端 | 网络、库、算力、身份体系 | CRUD、常见鉴权、单体 API | 分布式现实、可观测与可靠性、安全隔离、成本与弹性 |
| 安卓/iOS | 电量、后台、商店、厂商定制 | 常规 App、传感器调用模板 | 生命周期与功耗、商店规则、跨平台 vs 原生、硬件精细用法 |

共性：输入 → 算/存 → 输出。差别在底座给的通道和资源配额。AI 是增量层，会更快被迭代吃掉；真正拉开差距的是工程现实 + 跨层协同。

---

## 1. 桌面软件（Windows / macOS / Linux）

### 能力边界

受限于操作系统内核、驱动、硬件（CPU/GPU/内存/外设）和权限模型。

- **纯软件**：交互、图表、本地存储、算法计算。
- **外设 / 特殊硬件**：必须有官方或第三方 SDK + 对接文档（协议、时序、错误码），不能靠猜。

### 仍需深入（开任务时盯这些）

1. **资源生命周期（不只内存泄漏）**  
   句柄、线程、GPU 上下文、文件锁、设备会话。长时间运行后崩溃常在这块；还要管异步/并发下的资源竞争，以及崩溃转储分析（Windows WER、macOS Crash Reporter、Linux core + gdb）。
2. **跨平台 vs 原生**  
   Tauri / Electron / Flutter Desktop / Qt / WPF / SwiftUI / GTK——性能、包体积、更新机制、系统 API 暴露程度要按产品目标取舍，不是「哪个火用哪个」。
3. **硬件与系统深度集成**  
   音视频捕获、低延迟输入、后台服务、权限提升、自动更新、签名与安全策略。
4. **性能与可观测**  
   CPU/内存/IO Profiling、多线程与异步模型、与 GPU（CUDA / Metal / Vulkan / DirectML）协同。

### 桌面任务检查要点

- [ ] 外设有无对接文档？会话断开是否回收？
- [ ] 缓存/连接/定时器有上限和释放路径？
- [ ] 长时间跑有内存曲线或崩溃转储方案？
- [ ] 选型（Electron 等）的包体积与更新策略是否可接受？

## 2. 网站 / 前端

### 能力边界

浏览器沙箱是硬边界。可做：DOM / Canvas / WebGL / WebGPU、授权后的文件与部分传感器、Wasm、Service Worker、PWA；FFmpeg.wasm、WebRTC、Web Audio 等是边界内扩展，不是突破沙箱。

### 仍需深入

1. **边界内的精细利用**  
   WebGPU、OffscreenCanvas、WebCodecs、File System Access、Wasm + SIMD 的真实性能上限。
2. **工程化与性能**  
   Core Web Vitals、包体积、渲染管线、SPA 长会话内存泄漏、可访问性（a11y）。
3. **与后端 / 边缘的协作**  
   边缘函数与边缘渲染、实时同步（CRDT、WebSocket/SSE）——算力与权威数据仍宜下沉。
4. **安全模型**  
   CSP、CORS、SameSite、供应链攻击、客户端数据隔离。

### 前端任务检查要点

- [ ] 重计算是否进 Worker / 后端，避免卡主线程？
- [ ] 长会话是否有泄漏排查手段？
- [ ] 权限 API 失败降级是什么？
- [ ] CSP / 鉴权 Cookie 策略是否写进验收？

---

## 3. 后端 / 服务端

### 能力边界

网络、数据库、计算资源、身份与权限。主责：稳定数据服务、高并发与排队、会话/Token、数据隔离与安全。各端「看起来全能」，权威数据与权限闸门在后端。

### 仍需深入

1. **分布式现实**  
   一致性模型、幂等、重试与熔断、最终一致性、消息队列与事件驱动——不是「加个 Redis」就完事。
2. **可观测与可靠性**  
   指标、日志、链路追踪（OpenTelemetry）、SLO / 错误预算、混沌演练。
3. **安全与隔离**  
   OAuth2 / OIDC / Passkey、RBAC / ABAC、零信任、加密与隐私合规、密钥管理。
4. **成本与弹性**  
   Serverless vs 容器、自动伸缩、缓存、库选型与分片。

### 后端任务检查要点

- [ ] 写操作是否幂等？失败重试会不会双写？
- [ ] Token / 租户隔离是否可测、可审计？
- [ ] 有没有指标 + 追踪，而不只是打日志？
- [ ] 限流、超时、降级是否进验收？

## 4. 安卓（以及 iOS）

与桌面/Web 大同小异，多了移动端硬约束：

- 电量、后台限制、进程生命周期、动态权限、厂商定制兼容。
- 商店审核与分发、热更新限制、签名与安全检测。
- 传感器 / 相机 / 定位 / 蓝牙 / NFC 的精细用法与功耗。
- Flutter / RN / KMP vs 原生（Compose / SwiftUI）及混合架构取舍。

### 移动端任务检查要点

- [ ] 后台被杀后的恢复路径清楚吗？
- [ ] 权限拒绝时的产品路径？
- [ ] 真机矩阵（厂商/系统）是否覆盖验收？
- [ ] 外设/蓝牙是否有文档 + 功耗预算？

## 5. 当前真正值得投入的「增量」

传统缝隙基本填满。下面这些才是开专题、招人、排期时该押注的方向：

### 5.1 系统级思维与架构

不只写功能，而是长期可演进：模块边界、依赖方向、领域建模、可测试、可观测。Clean Architecture / Hexagonal、事件驱动、清晰数据流——在复杂项目里仍然值钱。

### 5.2 AI 应用工程（不是调 API）

纯调大模型已快成基础设施。仍需深入：

- 可靠的 RAG / 知识库构建与**评估**
- Agent 工作流、工具调用、状态管理与错误恢复
- 本地/边缘模型（量化、推理优化、隐私）
- 多模态端到端流水线（视觉、语音、文档）
- 评估体系：正确性、幻觉、延迟、成本
- AI 生成代码的审查与质量保障（加速开发，也引入正确性风险）

落地原则：AI 当可控插件；密钥与配额走后端；长任务异步；失败有降级，不当成无限能力。

### 5.3 可靠性与性能工程

内存问题只是冰山一角。难的是高并发、长时间运行、烂网络、硬件差异下的稳定。Profiling、火焰图、负载测试、容量规划仍是硬技能。

### 5.4 安全与合规的持续对抗

攻击面随 AI、供应链、云原生扩大。威胁建模、安全编码、隐私设计、SBOM 等供应链安全是持续需求。

### 5.5 跨层协同

前端 + 后端 + 移动 + AI + 数据 + 运维的端到端理解。单层的人很多；能设计整体数据流、权限模型、成本模型、故障域的人仍然稀缺。

## 6. 开任务用：能力边界卡（升级版）

每个开发任务开工前填一遍（比「边界是什么」多问「怎么做稳」）：

1. **目标形态**：桌面 / Web / 安卓 / iOS / 后端 / 组合  
2. **输入 / 输出通道**：是否有外设文档？授权失败怎么办？  
3. **数据权威**：本地还是后端？租户与鉴权怎么测？  
4. **资源与生命周期**：内存/句柄/会话上限；长时间运行策略；崩溃如何取证  
5. **并发与失败**：幂等、重试、熔断、断线恢复  
6. **可观测**：指标、日志、追踪、性能基线  
7. **安全**：Token、CSP/CORS、密钥位置、供应链  
8. **AI 是否介入**：哪一层、评估指标、降级路径、成本上限  
9. **验收不只功能**：要包含稳定性、性能、权限拒绝、异常网络中的表现

## 7. 务实学习 / 排期建议

- 不必再堆「入门框架怎么用」——已标准化。
- **选一个方向做深**：
  - 复杂业务 → 后端分布式 + 可观测 + 安全  
  - 高性能/本地体验 → 桌面或移动原生 + 性能分析 + 硬件集成  
  - 现代交互 → Web 高级 API + AI 前端集成 + 性能与 a11y  
  - 全栈/产品 → 端到端架构 + AI 应用工程  
- 用真实项目或开源验证：盯崩溃、性能退化、权限、数据一致性怎么定位和修。
- 跟踪的不是新框架名，而是**平台新能力**（浏览器/OS 新接口、推理优化）和**系统性问题**（成本、延迟、可靠性、安全）。

---

## 8. 收束

能力边界变清晰了，并不代表把系统做稳、做快、做对就变简单了。缝隙填满之后，价值在复杂系统的工程现实，以及 AI 集成层是否被当成可评估、可降级的工程问题来做。

若要再开更细专题，可直接点名一块（例如：桌面资源生命周期与崩溃取证、后端高并发与幂等、AI 应用架构与评估、或某一具体技术栈），再往下拆典型问题与学习/验收路径。
